# oeufcoque-mcp

マウスを動かす手を、MCP サーバーにしたものです。

座標を受け取ってカーソルをそこへ運び、押して、離して、**どこに着いて何を握っているかを返します**。それだけです。

---

## これは何ではないか

**目を持ちません。** `mouse_move(x=800, y=400)` は受け取りますが、800,400 に何があるかは答えられません。

ただし、**画面を見るほうの目は、作るものではない**かもしれません。実際に要るのはこれだけです。

```
画面を PNG に撮る  →  クライアントがその画像を読む  →  座標が決まる  →  oeufcoque が動かす
```

画像を読むのはクライアント自身です。撮るほうも Windows なら `CopyFromScreen` で数行なので、**視覚モデルを別に立てる必要がありません。**

このリポジトリにある `usb-webcam-mcp` / `wifi-cam-mcp` は物理世界を見るための目で、画面を見る目とは別物だと理解しています。oeufcoque が組む相手は視覚コンポーネントではなく、**スクリーンショット1枚**です。

### 撮ってから動かすまでの間に、画面は変わります

この流れの弱いところは、認識と行動の間に時間が空くことです。

実際に試したとき、撮影時に手前にあったウィンドウが、数十秒後に座標を問い合わせたときには別のウィンドウに変わっていました。**座標そのものは正しく、変わっていたのは画面のほうです。**

`mouse_state` は副作用なしで呼べるので、動かす直前に確かめるのに使えます。ただしそれで分かるのは座標とボタンの状態だけで、そこに何が表示されているかは分かりません。**撮り直すしかありません。**

---

## 入れる

```
uv tool install oeufcoque-mcp
```

`~/.claude.json`（あるいはお使いの MCP クライアントの設定）に:

```json
{
  "mcpServers": {
    "oeufcoque": {
      "command": "oeufcoque-mcp"
    }
  }
}
```

stdio なので、起こすのも終わらせるのもクライアントです。常駐させる操作はありません。

## ツール

| ツール | すること |
|---|---|
| `mouse_state` | 座標・ボタン状態・画面の広さ・ダブルクリック閾値を返す。**副作用なし** |
| `mouse_move(x, y)` | 曲線を描いて移動する |
| `mouse_click(button, count, x?, y?)` | クリック。`count=2` でダブルクリック |
| `mouse_drag(to_x, to_y, button, from_x?, from_y?)` | 押して、運んで、離す |
| `mouse_scroll(direction, amount, x?, y?)` | ホイールを回す |
| `mouse_release()` | 握ったままのボタンを離す（復旧用） |

`button` は `left` / `right` / `middle`。`left` は**主ボタン**の意味で、左右を入れ替えている環境ではそれに追従します。読み取り側（`GetAsyncKeyState`）も書き込み側（`SendInput`）も同じ規約なので、ここは一貫しています。

## 設計上の約束

### 押したら、必ず離す

**`press` ツールと `release` ツールはありません。** あるのは `drag` だけで、押下と解放が同じ関数の `try` / `finally` の中に入っています。

呼ぶ側が2回目の呼び出しを忘れてボタンが押しっぱなしになる、ということが起きません。忘れる対象の2回目が存在しないからです。ドキュメントの約束ではなく、構造で閉じています。

例外が出ても、クライアントが呼び出しをキャンセルしても、離します。

### 返すのは「動かしました」ではなく「どこにいるか」

すべてのツールが、実行後の座標とボタン状態を返します。**要求した値ではなく、OS から読み直した値です。**

他のものがカーソルを動かしていたら、あるいは入力がどこかで飲み込まれていたら、返り値がそう言います。

### 手はひとつ

カーソルは1画面に1本しかありませんが、stdio の MCP サーバーはクライアントのセッションごとに起動します。2つのセッションが同じカーソルを取り合えてしまう。

最初に起動したプロセスが名前付きミューテックスで手を握ります。握れなかったプロセスも起動はしますが、動かす系のツールを呼ばれると「他のセッションが持っています」と答えます（`mouse_state` は答えます）。

両方に持たせたい場合は `OEUFCOQUE_ALLOW_MULTIPLE=1`。

## 動きについて

直線では動きません。2次ベジェ曲線の制御点を、中点から**ランダムな角度**へ距離の 10〜25% ずらし、smoothstep で加減速し、手ぶれを ±1.5px 入れて終点に向けて減衰させます。到着直前の数ステップは揺れません。最後は必ず目標座標ぴったりに着きます。

ステップ数は `max(25, 距離/12)`。1000px の移動なら 84 点で、**実測しておよそ 1.3 秒**かかります。速くはありません。

この揺らぎは仕様です。決定論的に見えないのは不具合ではありません。

### ただし、時間方向のゆらぎは Windows では効いていません

1ステップごとに 8〜12ms のばらつきを入れているつもりでしたが、**実際には全部 15.6ms になっていました。**

| 要求した `sleep` | 実際にかかった時間（中央値・60回） |
|---|---|
| 8 ms | 15.53 ms |
| 10 ms | 15.70 ms |
| 12 ms | 15.84 ms |

Windows の既定のタイマー分解能が約 15.6ms なので、それより短い間隔はすべて同じ長さに丸められます。**8〜12ms という範囲は、まるごと分解能の下に沈んでいました。**

効いているのは空間方向のゆらぎ（制御点のランダムな角度と手ぶれ）だけで、時間方向は等間隔です。移動時間が設計値の 1.6 倍になっていたのも同じ理由でした。

`timeBeginPeriod(1)` で分解能を上げれば意図どおりに動きますが、プロセスの消費電力に影響するので入れていません。範囲を 8〜24ms のように分解能をまたぐ幅にすれば、丸めた先が 1 ティックか 2 ティックに割れて、ゆらぎが戻ります。**どちらもまだ試していません。**

## 測った値

`Windows 11 Pro 26200 / Python 3.12.10 / 96dpi 単一モニタ 1920x1080` で実測:

| 項目 | 値 |
|---|---|
| `GetDoubleClickTime()` | **500 ms** |
| `sizeof(INPUT)`（x64） | 40 bytes |
| 1000px の移動 | 84 ウェイポイント / 約 1.3 秒（15.6ms × 84 点。900px の辺の実測は 1.19 秒） |
| `asyncio.sleep(0.008〜0.012)` の実測 | いずれも **約 15.6 ms**（既定のタイマー分解能） |
| 依存パッケージ | `mcp` のみ。OS を叩く部分は `ctypes`（標準ライブラリ） |

### ダブルクリックの成立率

ダブルクリックの間隔は、システムの閾値の 25〜75% に収めています。**閾値より広い間隔で2回押したものは、ダブルクリックではなく2回のクリックです。**

ここを OS に聞かず、それらしい範囲（たとえば 0.2〜1.0 秒）から選ぶ実装にすると、**閾値 500ms を超える確率が 62.5%** になります。関数の名前がダブルクリックでも、6 割強は2回のクリックとして届く。しかも**成功と失敗が見た目で区別できない**ので、気づくきっかけがありません。

同じ審判で並べて測りました。判定は Tk の `<Double-Button-1>` に任せています。これはシステムの閾値そのもので発火するので、こちらの主張とは独立しています。

| | 20 回中の成立数 |
|---|---|
| 閾値を OS に聞く（oeufcoque） | **20 / 20** |
| 閾値を聞かず 0.2〜1.0 秒から選ぶ | **8 / 20**（20 回中 12 回が閾値超え） |

閾値は環境ごとに違います。この数字は「500ms の環境で 0.2〜1.0 秒を選ぶとこうなる」という一例で、**移植可能なのは値ではなく「OS に聞く」という手続きのほうです。**

## テスト

```
uv run python tests/test_hand.py      # 何も動かさない。13 件
uv run python tests/manual_target.py  # 実機。カーソルが動く。10 件
```

`test_hand.py` は偽のバックエンドを使うので、デスクトップのない環境でも走ります。`drag` の途中で例外が出た場合と、呼び出しがキャンセルされた場合に、ボタンが必ず離れることを確かめています。

`manual_target.py` は**自分で的のウィンドウを立てて、そこだけを叩きます**。他人のウィンドウは触りません。入力が「OS を通ってアプリに、狙った座標で届いた」ことを、受け取り側で確認します。上の成立率もこれで測っています。

## できないこと

**昇格したウィンドウには届きません。** UIPI により、より高い整合性レベルで動いているアプリケーションへは入力を注入できません。管理者権限のアプリの上では、呼び出しは成功して何も起きません。`SendInput` が受理数を返すので、受理されなかった場合はエラーにしていますが、**受理された上で無視される経路は検出できません**。

**プロセスを強制終了されると、握ったままになります。** `atexit` と `SIGINT` / `SIGTERM` は拾いますが、`TerminateProcess` や `SIGKILL` は拾えません。ドラッグの途中で殺されると、ボタンは押されたままになります。プロセス内のどんな仕組みでもこれは防げません。`mouse_release` はそのための戻り道です。

**DPI スケーリング環境は未検証です。** 起動時に per-monitor-v2 の DPI 認識を宣言して座標系を曖昧にしないようにしていますが、確認できたのは 96dpi・単一モニタの環境だけです。スケーリングやマルチモニタでの挙動は測っていません。

ここは上の流れの要でもあります。**撮った画像の座標と `SetCursorPos` の座標が同じ空間でないと、見えていても押せません。** 96dpi・単一モニタでは一致することを確かめました（画像から拾った座標を `WindowFromPoint` に渡し、見えていたウィンドウが返ってくることを確認）。スケーリングのかかった環境では、**撮る側も同じ DPI 認識を宣言している必要があります。**

**Windows 以外は未実装です。** 下記。

## 移植する

OS を触るのは `backend/` の中だけです。その上（経路、イージング、タイミング、握っているものの管理、ツールの形）はプラットフォームに依存しません。

```
backend/windows.py        user32.dll / ctypes       実装済み
backend/darwin.py         Quartz Event Services     未着手
backend/linux_x11.py      XTEST / python-xlib       未着手
backend/linux_wayland.py  libei / portal            設計上むずかしい
```

`Backend` プロトコル（9個の小さな関数）を満たすモジュールを1つ足して、`get_backend()` の分岐に加えるだけです。それ以外は書き換える必要がありません。

Wayland だけは言語やライブラリの問題ではありません。合成器が「任意のアプリが他のアプリに入力を注入すること」を設計として許していないので、portal 経由でユーザーの明示的な許可を取るか、`uinput` を直接叩く（権限が要る）ことになります。
